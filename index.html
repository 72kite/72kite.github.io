    Professional self-assessment

    I build software across the stack, and the work I care most about is the part users never see: the decision underneath the screen. My capstone took an Android inventory app I wrote earlier in the program and rebuilt it three times over — once for structure, once for speed, once for safety. Before any of that, I already understood the problem it solves: I coordinate a team and a stock count every shift as a retail Team Lead, and this app is a rebuild of a process I already run by hand.

    Most of my coursework was completed independently, so I treated documentation and architecture as a stand-in for a teammate who wasn't in the room — a Repository layer that lets someone swap the data source without touching the UI is the same instinct that keeps a team aligned when the person coordinating it changes shift to shift. Translating technical work for people outside engineering is a skill I built the same way, training volunteers on AV systems and, in coursework like CS 255's client-interview case study, extracting real requirements from how a stakeholder actually talks about their problem rather than from a specification document. This portfolio applies the same instinct: one codebase, presented three different ways for three different readers.

    Algorithmically, the enhancement I'm proudest of replaced a full linear scan with the hand-built prefix tree above — O(k) instead of O(n), independent of inventory size — paired with a stable custom MergeSort, and proven with unit tests rather than just asserted in a comment.

    What the rest of the process taught me is that structure, speed, and safety are the same skill. A Repository sitting between the ViewModel and the data layer is what made swapping raw SQLite for an encrypted Room database a contained change rather than a rewrite — the same seam let me add a foreign-key-scoped schema migration, verified against a real pre-migration database file, without the UI layer needing to change at all.

    Security, to me, is a design constraint, not a task filed for after launch: passwords are hashed with PBKDF2 and a per-user salt, the database is encrypted at rest behind a passphrase that's never a literal value in source, and where I couldn't fully close a gap — this app's Google sign-in has no backend to verify tokens against — I documented that trust boundary honestly instead of implying a guarantee the architecture doesn't actually provide. That's the kind of software engineering work I'm looking for next.

    Software design & engineering

    Complete

    The original app put database calls directly in its Activities, using a hand-written SQLiteOpenHelper and synchronous calls on whatever thread invoked them. I rebuilt it as a Kotlin MVVM architecture — Activity → ViewModel → Repository → DAO — over coroutines and Flow, so the UI asks for inventory without knowing where it lives or how it's fetched. The legacy Java Activities and the two parallel, unsynchronized data layers left behind from an earlier incomplete migration are gone; a restored instrumented test suite covers the real Room database that replaced them.

    Kotlin · Android · MVVM · Repository pattern · Coroutines · Flow · LiveData

    Algorithms & data structures

    Complete

    Search was a full-table scan on every keystroke. I designed a Trie index that resolves a prefix in steps proportional to the length of the query instead of the size of the inventory, plus a stable MergeSort pass for predictable ordering. The demo at the top of this page runs the same structure in the browser. In the app, the Repository rebuilds the index from Room's reactive query stream and keeps it scoped to whichever user is signed in, with a JUnit suite covering both structures independent of Android.

    Databases

    Complete

    The app stored inventory in an unencrypted SQLite file — readable by anyone who pulled it off the device — and hashed nothing. I migrated it to Room backed by SQLCipher with 256-bit AES, moved the passphrase out of the source and into Keystore-backed runtime storage, and replaced plaintext password comparison with PBKDF2 and a per-user salt. The proof is in the first sixteen bytes of the database file:

    before 53 51 4C 69 74 65 20 66 6F 72 6D 61 74 20 33 00 → "SQLite format 3"
    after A7 3C 1E 90 44 D2 0B 5F E1 88 7A 33 C6 09 2D B4 → ciphertext

    The schema change under that encryption — adding a foreign key that scopes every item to its owner — runs through a real Migration, not a destructive fallback. It's now verified by replaying it against an actual pre-migration database file on a physical device, not just a diff against the target schema.

    Kotlin · Room · SQLCipher · SQLite · AES-256 · PBKDF2
