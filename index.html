    A prefix tree walks one node per character you type. A linear scan checks every item, every keystroke. Grow the inventory to 10,000 items and the right-hand number becomes 10,000 — the left-hand number stays exactly where it is. That property is the reason I replaced the search in my capstone project.

    Capstone enhancements · CS 499

    Software design & engineering

    Complete

    The original app put database calls directly in its Activities, using a hand-written SQLiteOpenHelper and synchronous calls on whatever thread invoked them. I rebuilt it as a Kotlin MVVM architecture — Activity → ViewModel → Repository → DAO — over coroutines and Flow, so the UI asks for inventory without knowing where it lives or how it's fetched. The legacy Java Activities and the two parallel, unsynchronized data layers left behind from an earlier incomplete migration are gone; a restored instrumented test suite covers the real Room database that replaced them.

    Kotlin · Android · MVVM · Repository pattern · Coroutines · Flow · LiveData

    Algorithms & data structures

    Complete

    Search was a full-table scan on every keystroke. I designed a Trie index that resolves a prefix in steps proportional to the length of the query instead of the size of the inventory, plus a stable MergeSort pass for predictable ordering. The demo at the top of this page runs the same structure in the browser. In the app, the Repository rebuilds the index from Room's reactive query stream and keeps it scoped to whichever user is signed in, with a JUnit suite covering both structures independent of Android.

    Java · Trie / prefix tree · MergeSort · JUnit

    Databases

    Complete

    The app stored inventory in an unencrypted SQLite file — readable by anyone who pulled it off the device — and hashed nothing. I migrated it to Room backed by SQLCipher with 256-bit AES, moved the passphrase out of the source and into Keystore-backed runtime storage, and replaced plaintext password comparison with PBKDF2 and a per-user salt. The proof is in the first sixteen bytes of the database file:

    before 53 51 4C 69 74 65 20 66 6F 72 6D 61 74 20 33 00 → "SQLite format 3"
    after A7 3C 1E 90 44 D2 0B 5F E1 88 7A 33 C6 09 2D B4 → ciphertext

    The schema change under that encryption — adding a foreign key that scopes every item to its owner — runs through a real Migration, not a destructive fallback. It's now verified by replaying it against an actual pre-migration database file on a physical device, not just a diff against the target schema.

    Kotlin · Room · SQLCipher · SQLite · AES-256 · PBKDF2
