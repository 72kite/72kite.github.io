Professional self-assessment

← Back to portfolio

I build software across the stack, and the work I care most about is the part users never see: the decision underneath the screen. My capstone took an Android inventory app I wrote earlier in the program and rebuilt it three times over — once for structure, once for speed, once for safety. Before any of that, I already understood the problem it solves: I coordinate a team and a stock count every shift as a retail Team Lead, and this app is a rebuild of a process I already run by hand.

Most of my coursework was completed independently, so I treated documentation and architecture as a stand-in for a teammate who wasn't in the room — a Repository layer that lets someone swap the data source without touching the UI is the same instinct that keeps a team aligned when the person coordinating it changes shift to shift. Translating technical work for people outside engineering is a skill I built the same way, training volunteers on AV systems and, in coursework like CS 255's client-interview case study, extracting real requirements from how a stakeholder actually talks about their problem rather than from a specification document. This portfolio applies the same instinct: one codebase, presented three different ways for three different readers.

Algorithmically, the enhancement I'm proudest of replaced a full linear scan with the hand-built prefix tree on the homepage — O(k) instead of O(n), independent of inventory size — paired with a stable custom MergeSort, and proven with unit tests rather than just asserted in a comment.

What the rest of the process taught me is that structure, speed, and safety are the same skill. A Repository sitting between the ViewModel and the data layer is what made swapping raw SQLite for an encrypted Room database a contained change rather than a rewrite — the same seam let me add a foreign-key-scoped schema migration, verified against a real pre-migration database file, without the UI layer needing to change at all.

Security, to me, is a design constraint, not a task filed for after launch: passwords are hashed with PBKDF2 and a per-user salt, the database is encrypted at rest behind a passphrase that's never a literal value in source, and where I couldn't fully close a gap — this app's Google sign-in has no backend to verify tokens against — I documented that trust boundary honestly instead of implying a guarantee the architecture doesn't actually provide. That's the kind of software engineering work I'm looking for next.
